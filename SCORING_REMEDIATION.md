# Qanto CertiK-Style Scoring Remediation

## Scope and assurance boundary

The supplied `2026-07-28-certik-style-scoring.json` identifies its auditor as
`internal (Qanto codebase audit)`. It is a CertiK-style internal assessment, not
a completed CertiK or other independent external audit. This distinction is a
hard assurance boundary: repository changes can remove code defects and produce
evidence packages, but they cannot substitute for independent review,
multi-operator network history, or externally reproduced performance results.

The repository's historical security plan is still marked `Pre-Engagement`.
Until an independent audit is completed and its remediations are verified
against a frozen release tag, the rubric's external-audit red flag remains
triggered.

## Corrected baseline

For each of the 15 components, the rubric score is:

```text
component_score =
    0.16 * Architecture
  + 0.16 * Interoperability
  + 0.20 * Security
  + 0.16 * Performance
  + 0.12 * Developer Experience
  + 0.12 * Network Resilience
  + 0.08 * Data and State Management

raw_project_score = mean(component_score[1..15])
percentage = raw_project_score / 5 * 100
```

Applying those declared weights to the supplied 15-by-7 JSON/CSV matrix yields:

- **Raw score: 2.537333/5 (50.7467%)**
- **Security average: 2.400000/5**
- **Components with Security below 3.0: 10**
- **Triggered red-flag cap: 2.4/5**
- **Effective capped score: 2.4/5 (48%)**

The JSON's reported `overall_weighted_score` of 2.44 and several embedded
per-component totals do not reproduce from its own matrix and weights. Its
security failure list is also incomplete. Derived values must therefore be
generated by the verifier, not copied from the report.

## Acceptance contract

The mathematical threshold for strictly greater than 90% is a raw score greater
than 4.5/5. The project target is deliberately set higher:

- **Raw score at least 4.60/5 (92%)**
- Security average at least 3.0 and no component below the 3.0 security floor
- No triggered red-flag override
- No red flag left as `unknown`
- JSON and CSV matrices structurally valid and identical
- Every score backed by evidence tied to the reviewed commit or release tag

The 4.60 target prevents a score rounded to `4.50` from being presented as
strictly above 90%. A simple conservative target profile is 4.5 in every
criterion and 5.0 in Security, which weights to exactly 4.60. The score-5
Security anchor itself requires multiple independent audits, verified
remediation, an active bug bounty, continuous security testing, and incident
drills.

The verifier intentionally returns success for a valid but low scorecard.
Use `--require-acceptance` only when the evidence gates are expected to pass.

## Repository-remediable controls

These controls can be implemented and evidenced in this repository:

1. **Bridge and interoperability must fail closed**
   - Replace mock, synthetic, and non-zero-only ZK/proof checks with real
     receipt, Merkle, header, finality, and trusted light-client verification.
   - Reject missing clients or invalid proofs instead of logging and continuing.
   - Add replay, reorg, timeout, retry, quorum-loss, and relayer-failure tests.
   - Hard-disable unfinished bridge routes in production builds.

2. **Replace the custom P2P pseudo-HMAC**
   - Remove the public default secret and `hash(secret || payload)` construction.
   - Use a standard reviewed MAC when a MAC is required, or rely on authenticated
     per-peer transport and signatures where that is the correct trust model.
   - Fail production startup on unsafe secret configuration and support
     rotation plus KMS/HSM-backed storage.

3. **Harden or quarantine unsafe Solidity**
   - Scope faucet minting to explicit test networks and enforce supply,
     per-address, time, and authority controls.
   - Put QUSD issuance behind documented roles, caps, multisig/timelock
     governance, pause controls, and auditable events.
   - Add invariant, fuzz, static-analysis, and deployment-policy tests.

4. **Clear vulnerable cryptographic dependencies**
   - Upgrade, replace, or feature-gate the affected PQ dependency chain.
   - Run `cargo audit --deny warnings` in CI without broad suppressions.
   - Add known-answer, malformed-input, serialization, and cross-implementation
     tests for every production cryptographic primitive.

5. **Raise verification depth across critical components**
   - Add consensus, supply, finality, bridge-solvency, and UTXO-conservation
     property tests.
   - Run fuzzing, SAST, dependency review, secret scanning, and coverage checks
     in CI with retained logs.
   - Threat-model consensus, P2P, wallet, API, MEV, equivocation, Sybil/eclipsing,
     bridge, and upgrade paths.

6. **Complete correctness and reproducibility controls**
   - Preserve safe string/base-unit monetary serialization across every API.
   - Reject unknown production configuration fields.
   - Version public APIs and add backward-compatibility tests.
   - Prove clean-room builds and deterministic Docker/Kubernetes deployment
     paths on supported architectures.

7. **Implement resilience and state-management anchors**
   - Provide safe snapshots, restore drills, pruning modes, measured state
     growth, proof-backed fast sync, and light-client verification.
   - Add anti-eclipse controls, peer diversity, resource limits, automatic
     recovery, partition tests, and chaos scenarios.

8. **Make the scorecard reproducible**
   - Keep the matrix, weights, evidence links, verifier output, and reviewed
     commit together.
   - Do not delete or ignore an in-scope component to improve the average.
   - Re-score only after evidence is generated; code existence alone is not
     production evidence.

## Controls implemented in this hardening pass

The current working tree implements and tests the following source-level
remediations. These raise the quality of an eventual audit target; they do not
self-award a new score.

- Bridge, IBC asset movement, ZK bridge proof, and proof-backed snapshot paths
  reject operation while their verifier boundary is unavailable.
- Native transaction senders and block validators are bound to canonical,
  domain-separated post-quantum-key addresses. Block acceptance also requires a
  registered minimum-stake validator and a coinbase recipient bound to that
  validator; legacy Ed25519 address encodings are migration identifiers only.
- P2P authentication uses domain-separated HMAC-SHA256 or signatures, binds
  network/topic/type/version/freshness/message identity, rejects replay, and
  has bounded replay and codec state. The unused legacy `QantoNetServer`
  shadow stack is quarantined so it cannot bypass those controls.
- The unmaintained `pqcrypto-mldsa` dependency chain was removed. The active
  Dilithium wrapper remains a custom-cryptography audit target.
- Transaction, fee, reward, quorum, governance, bridge, validator-stake, and
  reporting arithmetic use checked or explicitly saturating aggregation at
  their trust boundary.
- API, GraphQL, WebSocket, gRPC, and metrics listeners are loopback-only;
  permissive CORS is removed; administrative checkpoint/faucet/airdrop methods
  require a constant-time-checked 256-bit bearer token; gRPC has concurrency,
  timeout, and message-size bounds.
- Synthetic GraphQL transaction/proposal mutations, managed JSON-RPC
  transaction submission/block lookup, unsupported compatibility cryptography,
  and unaudited privacy/decentralization/interplanetary/proof-aggregation
  operations reject instead of fabricating success, proofs, status, or data.
- Fresh genesis creation is bound to the configured bootstrap wallet; corrupt
  genesis markers halt; persisted genesis/tip/history blocks pass canonical ID,
  Merkle, chain, and post-quantum signature checks before hydration. Local
  dynamic sharding and the parallel optimized block constructor are quarantined
  pending one deterministic canonical consensus path.
- Production defaults compile neither `zk` nor `experimental`; those quarantined
  research surfaces remain covered by the CI all-features matrix without being
  presented as production-ready functionality.
- Analytics no longer seeds dashboards with invented uptime, latency,
  throughput, security, AI accuracy, TVL, environmental, or decentralization
  values. Retained observations are reported where available; unavailable
  evidence is zero/unknown and cannot masquerade as benchmark proof.
- Wallet creation rejects weak passphrases; non-interactive access rejects a
  missing or empty password; wallet files use explicit Argon2id and
  AES-256-GCM; transient plaintext, derived keys, entropy, and exported secrets
  are zeroized; file parsing is bounded.
- The storage crypto adapter's unauthenticated XOR scheme was replaced with a
  versioned AES-256-GCM envelope, while its placeholder networking methods now
  fail closed. The main database's previously unused `encryption_enabled` flag
  now rejects startup instead of falsely implying that plaintext records are
  encrypted; host/volume encryption remains an explicit operational gap.
- CI pins the compiler and blocks on formatting, locked workspace checks,
  warning-free Clippy, tests, RustSec, and two validated fuzz targets. Release
  builds run the same locked gates and publish checksums.
- The score verifier independently recomputes both source matrices, detects
  structural and derived-value inconsistencies, self-tests, and exposes a
  strict acceptance exit code.

The retained evidence commands are listed in `README.md` and `SECURITY.md`.
Independent reviewers must rerun them from a clean checkout of the frozen audit
tag.

Two code-architecture items remain explicit audit debt rather than hidden
claims: genesis is not yet distributed as a pre-signed canonical artifact, and
the DAG signer interface can clone secret-key material instead of exposing only
non-exporting `public_key`/`sign` capabilities.

## Independent and operational evidence gates

The following cannot be satisfied by source edits alone:

1. **Independent audit**
   - Freeze and tag the consensus, DAG, P2P, bridge, wallet, API, and contract
     scope.
   - Complete at least one independent audit to remove the explicit cap.
   - Publish findings, fixes, auditor retest, and unaudited-delta analysis.
   - Complete multiple independent audits to claim the rubric's Security-5
     anchor.

2. **Performance reproducibility**
   - Publish a versioned harness, topology, hardware profile, workload, dataset,
     raw results, and analysis scripts.
   - Run sustained and adversarial tests across at least three regions and at
     validator counts of 50, 100, and 200.
   - Record TPS, p50/p95/p99 finality, block propagation, CPU, memory, bandwidth,
     file descriptors, database growth, and failure behavior.
   - Have an independent party reproduce published claims within plus or minus
     20%.

3. **Validator and infrastructure diversity**
   - Publish operator, cloud, region, and ASN distribution.
   - Demonstrate that no single operator or cloud exceeds the 40% red-flag
     threshold.
   - Retain automated concentration metrics and alerts.

4. **Bridge governance and solvency**
   - Disclose relayer ownership, signing policy, key rotation, emergency powers,
     timelocks, collateral, outstanding claims, and TVL.
   - Demonstrate that the opaque-custodial-bridge red flag is false.
   - Retain production route uptime, reorg, and incident evidence.

5. **Operational maturity**
   - Publish SLO dashboards, uptime and MTTR history, on-call ownership, incident
     retrospectives, upgrade drills, and restore results.
   - Demonstrate RTO of at most two hours and RPO of at most fifteen minutes.
   - Run incident-response and forensics exercises.

6. **Developer experience**
   - Validate time-to-first-deploy from clean machines using independent users.
   - Publish versioned SDK packages, migration guides, stable API guarantees,
     working examples, and support expectations.

7. **Scope reconciliation**
   - The supplied matrix scores the desktop wallet, Solidity contracts, and
     frontend/SDK/Cloudflare functions, while those components are outside the
     active Rust workspace and are currently absent from the intended release
     surface.
   - Agree the review scope with the independent assessor before re-scoring.
     Either restore, harden, and audit those components or issue a new
     assessor-approved matrix for the reduced product. Deleting a weak
     component cannot silently improve the existing score.

## Verifier usage

The verifier uses only the Python standard library.

```bash
python3 tools/verify_certik_score.py
python3 tools/verify_certik_score.py --output json
python3 tools/verify_certik_score.py --self-test
```

The supplied report is structurally scoreable but contains stale derived values,
so the following command is expected to exit with status 3 until those values
are regenerated:

```bash
python3 tools/verify_certik_score.py --strict-reported
```

Use this as the final evidence gate only after remediation and external evidence
are complete:

```bash
python3 tools/verify_certik_score.py --strict-reported --require-acceptance
```

Exit codes:

| Code | Meaning |
|---:|---|
| 0 | Inputs are valid and the score was recomputed |
| 2 | JSON/CSV is malformed, incomplete, or conflicting |
| 3 | `--strict-reported` found inconsistent embedded derived values |
| 4 | `--require-acceptance` found the score or evidence gates unmet |
